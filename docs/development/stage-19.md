# 第十九阶段 · 伙伴技能与 Git 分支交付

## 伙伴如何选择技能

每位工作伙伴有自己的手工指南和 GitHub 来源配置。委托提交时复制这份配置。规划器可以看到技能名和简介，执行者或复核者只会收到分配给自己的技能正文。早期委托没有技能字段，沿用原有分工。

开启自动发现并为本次委托授权 `api.github.com` 后，伙伴可在 GitHub 的公开仓库索引中按主题查找技能来源。自动发现只接受未归档、至少有 100 个 stars 的公共仓库。也可以为个别伙伴进一步限定仓库。发往 GitHub 的全站检索词是公开技术关键词；具体文件路径的匹配在本机进行。

模型选取候选仓库后，运行时解析默认分支的提交和 Git 树，查找实际的 `SKILL.md`。下载时再次校验仓库资格和固定文件的路径、字节数、Git blob 哈希，再保存正文、来源及使用记录。

同一任务重启后可以使用已固定的正文。外部技能不会授予进程执行权，普通网页读取也限于本任务已固定的来源，重定向逐跳检查。脚本、依赖和外链附件不在自动下载范围内。GitHub 匿名 API 可能限流，失败原因和可用的重试时间会返回给伙伴。[技能运行测试](../../tests/integration/github-skills.test.ts) · [角色设置测试](../../tests/e2e/character-settings.spec.ts)

## 从成果验收到远端分支

1. 导入使用 GitHub HTTPS `origin` 的普通 Git 仓库，创建委托时可选择验收后提醒推送。全部当前成果通过复核并被接受后，回信匣会出现“确认 Git 分支交付”。
2. 在成果面板生成预览。工作室以远端默认分支的固定提交为基线，逐个核对导入时的文件基线和已验收成果的不可变字节，显示路径和差异。未提交的本地代码、未推送的本地提交、暂存区内容和未验收成果都会留在原处。
3. 用户核对系统确认窗口中的远端、基线和新分支后，才会发起推送。远端目标已被其他提交占用时会阻止交付。推送中断后，使用原操作编号核查远端，可以识别实际已经送达的提交。
4. 已发布的回执保留当时的提交哈希。“核查远端分支”可确认该分支现在是否仍指向这个提交。打开 GitHub 比较页时也会重查分支；创建 PR 的最后一步在 GitHub 页面完成。公开 PR 查询只接受与仓库、目标、来源分支和已推送提交对应的记录，面板显示该提交的检查状态。

本阶段使用隔离的 bare 仓库实际运行 Git，覆盖本地未提交改动、CRLF、并发预览、取消、分支占用、丢失回执和重试。Electron 用例经 preload、主进程系统确认与运行时，在真实 Git 远端核对文件字节及默认分支。[Git 交付集成测试](../../tests/integration/git-delivery.test.ts) · [桌面端到端验收](../../tests/e2e/git-delivery-desktop.spec.ts) · [PR 状态绑定测试](../../tests/integration/git-pr-status.test.ts)
